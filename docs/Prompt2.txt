# BUILD SPECIFICATION

## Automated Brazilian RBC Research Agent

You are helping build an agent that continuously researches and monitors Brazilian Renda Básica de Cidadania (RBC) developments.

The agent already has an ingestion/knowledge-base system.

The next development phase is:

1. Add topic tagging to ingestion.
2. Build `research_topic`.
3. Build `summarize_topic_updates`.
4. Create a scheduled GitHub Action that runs the research and update-summary pipeline weekly.

The goal is not merely to make a generic web-search agent.

The goal is to create a **longitudinal research system** that knows what it already knows, searches for new evidence, detects changes, avoids duplicate reporting, preserves historical state, and produces a concise weekly RBC update.

---

# 1. TOPIC MODEL

Add a topic field to `knowledge_chunks`.

Minimum concept:

```text
topic
```

Recommended value for the current project:

```text
brazil-rbc
```

However, design the field so future topics can be added.

Potential future examples:

```text
brazil-rbc
cadunico-digital
international-basic-income
municipal-social-currency
```

Do not hard-code the system so that only RBC can ever exist.

The topic should be queryable and filterable.

---

# 2. RESEARCH TOPIC TOOL

Build:

```text
research_topic
```

Purpose:

> Search the web for new information related to a specific research topic, compare it against the existing knowledge base, and ingest relevant new evidence.

Conceptual input:

```json
{
  "topic": "brazil-rbc",
  "since": "optional date",
  "scope": "optional",
  "force_full_scan": false
}
```

The implementation may use a different schema if that better fits the existing agent architecture.

---

# 3. RESEARCH TOPIC BEHAVIOR

When `research_topic` is called for `brazil-rbc`, it should:

### Step A — Load existing knowledge

Retrieve existing knowledge chunks tagged:

```text
brazil-rbc
```

The agent must understand the existing state before searching.

This is critical.

The system should not simply search and append articles.

---

### Step B — Search official sources first

Search priority:

1. municipal government;
2. municipal legislative chambers;
3. Diário Oficial;
4. state legislative assemblies;
5. state governments;
6. Câmara dos Deputados;
7. Senado;
8. Planalto;
9. MDS / gov.br;
10. other federal ministries/agencies;
11. high-quality secondary sources;
12. discovery-only sources.

The agent should use secondary sources primarily to discover leads and then attempt official verification.

# 5. CLASSIFICATION

Every research result must be classified:

```text
A = True / close RBC
B = Maricá-inspired / social-currency income
C = Ordinary targeted social assistance
```

Do not classify by title alone.

Evaluate the actual program/proposal.

---

# 6. CHANGE DETECTION

This is the most important feature of `summarize_topic_updates`.

The system must distinguish:

```text
NEW
CHANGED
UNCHANGED
HISTORICAL
UNVERIFIED
```

For example:

Existing knowledge:

```text
PL 107/2023
Status: first discussion approved
Date: 2025-08-27
```

New search result:

```text
Official Câmara page
Status: first discussion approved
```

Result:

```text
UNCHANGED
```

Do not report it as a new development.

If the new result says:

```text
Scheduled for second discussion
```

Result:

```text
CHANGED
```

If the new result says:

```text
Second discussion approved
```

Result:

```text
CHANGED
```

The system must preserve both states:

```text
previous_status
new_status
```

---

# 7. HISTORICAL STATE

Do not replace old knowledge with new knowledge.

For legislative monitoring, preserve a timeline such as:

```text
2023-03-21 — PL introduced
2024 — committee opinions
2025-08-27 — first discussion approved
2026-09-XX — second discussion scheduled
...
```

This makes the database longitudinal rather than simply a collection of current articles.

---

# 8. DEDUPLICATION

The agent must recognize duplicate reporting.

For example:

Five newspapers reporting the same Câmara vote should NOT become five separate "updates."

Prefer the primary official source.

Store secondary sources as corroborating evidence when useful.

The final weekly report should normally report the event once.

---

# 11. `summarize_topic_updates`

Build:

```text
summarize_topic_updates
```

Purpose:

> Read the newly researched evidence together with the existing knowledge and produce a concise explanation of what actually changed.

It should NOT simply summarize the newest search results.

It must answer:

1. What changed?
2. Where?
3. When?
4. What was the previous status?
5. What is the new status?
6. Is it Category A, B or C?
7. Is the source official?
8. Why is this relevant to the RBC research?
9. What should be monitored next?

---

The GitHub Action should ultimately produce something similar to:

```text
- New municipal RBC proposals
- Maricá-inspired programs

Only include this section when there are genuinely relevant leads lacking official confirmation.
```

Do not fill the report with unchanged information merely to make it longer.

---

# 13. SPECIAL RULE FOR "NO CHANGE"

"No change found" is a valid research result.

For high-priority entities, explicitly report:

```text
No new official movement found in the sources checked during this cycle.
```

Do not say:

```text
Nothing happened.
```

because the agent cannot prove that.

It can only report what it checked.




---

# 16. FAILURE HANDLING

The workflow must not silently claim that research succeeded.

If:

* search fails;
* official source is unavailable;
* API fails;
* rate limit occurs;
* summarization fails;
* delivery fails;

the GitHub Action should clearly report the failure.

A partial research result must be labeled as partial.

---

# 17. SECURITY

Never put:

* API keys;
* email credentials;
* webhook secrets;
* tokens;

inside the prompt, source code or database records.

Use GitHub Secrets/environment variables.

Do not expose credentials in logs.

---

# 18. COST / EFFICIENCY

The research agent should avoid unnecessary repeated work.

Use:

* existing knowledge;
* previous source URLs;
* publication dates;
* entity status;
* topic tags;
* incremental searches.

A weekly research cycle should prioritize likely-new material rather than repeatedly crawling the entire historical internet.

However, periodically perform broader discovery scans so that the system does not become blind to newly emerging municipalities or terminology.

---

# 19. IMPORTANT: DO NOT LOSE THE USER'S RESEARCH DISTINCTIONS

The agent must preserve these distinctions:

```text
RBC ≠ every cash-transfer program

RBC ≠ every social currency

Maricá-inspired ≠ automatically universal RBC

Targeted social assistance ≠ RBC

Historical proposal ≠ current implementation

Proposal ≠ approved law

Approved law ≠ implemented program

First vote ≠ second vote

Secondary report ≠ official confirmation
```

These distinctions are fundamental to the project.

---

# 20. EXPECTED RESULT

After implementation, the user should be able to run something conceptually equivalent to:

```text
research_topic("brazil-rbc")
```

and have the agent discover new evidence.

Then:

```text
summarize_topic_updates("brazil-rbc")
```

should explain only what changed relative to the existing knowledge base.

The weekly GitHub Action should automate both operations and deliver the resulting report.

The final system should function as a **persistent RBC research monitor**, not as a one-time web-search chatbot.
